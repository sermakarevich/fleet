# tweet_watch R9 (schedule install and verify) — failure modes

Scope: installed recurring schedule `fleet schedule create --name
tweet-watch --cron '*/30 * * * *' --overlap skip` with coder `opencode`,
verified by `fleet schedule list` showing `tweet-watch` and one manual
`fleet schedule run` completing. Observable: `schedule list` contains
the entry; the manual run executes R1-R6 once.
Step-level edge cases (fetch/parse, scoring, dedupe, gating,
persistence, file formats) live in M1/M2/M3 and R1-R6; this file
covers the schedule only: wrong install arguments, a broken or
missing scheduler, a verify run that hits a bad runtime situation,
and what the installer must do instead of improvising (stop and
report, never invent names, crons, flags, or coders).

The install names these exact facts — any deviation is an install
bug:
name `tweet-watch`, cron `*/30 * * * *`, `--overlap skip`, coder
`opencode`; verify is `fleet schedule list` plus exactly one manual
`fleet schedule run`; the manual run performs one R1-R6 pass and
nothing else (no replay loops, no catch-up multipliers).

## Bad or missing input

- F1 schedule created with the wrong name (`tweet_watch`,
  `tweetwatch`, `tweet-watch-v2` as a "backup"). Expected: error —
  delete the wrongly-named entry and reinstall as `tweet-watch`. A
  variant name forks the worker: the 30-minute tick fires under a
  name nobody verifies, and `schedule list | grep tweet-watch` gives
  false confidence from the wrong row.
- F2 schedule created with the wrong cron (`* * * * *` every minute,
  `0 * * * *` hourly, `*/30 * * *` missing a field). Expected: error
  naming the expected cron `*/30 * * * *`. Every-minute polls spam
  the operator with re-proposals on transient failures; hourly loses
  the 30-minute freshness contract. Fix by deleting and recreating —
  never "leave it, close enough".
- F3 schedule created without `--overlap skip` (flag omitted, or
  `--overlap allow`/`queue`). Expected: reinstall with `--overlap
  skip`. Without skip a slow run (large backlog, several HIGH
  proposals waiting on the operator console) piles a second run on
  top of the first; both propose independently and the operator gets
  duplicate `ask_human` calls for the same tweets.
- F4 schedule created with the wrong coder (coder omitted so it
  defaults, or a different coder name). Expected: error naming coder
  `opencode`. The wrong coder may lack the `x` CLI, the KB paths, or
  the `ask_human` tool, so the tick fails every 30 minutes in a way
  the manual verify run (done under the right coder) never showed.
- F5 cron passed unquoted or shell-mangled (`--cron */30 * * * *`
  without quotes, so the shell expands `*/30` against local files).
  Expected: the create command fails or installs a garbage schedule —
  abort, re-run with single quotes exactly as documented. Verify with
  `schedule list` showing the cron field as `*/30 * * * *`, not a
  file list.
- F6 schedule created from the wrong directory or wrong fleet context
  (installer runs `fleet schedule create` outside
  `/Users/sergii/git/fleet`, so the tick checks out the wrong repo or
  no repo). Expected: error — the schedule must be owned by the fleet
  repo checkout. Delete the mis-scoped entry and recreate from the
  repo root.
- F7 `fleet` CLI missing on the install machine (`command not found`).
  Expected: hard stop with an error naming the missing CLI. Never
  substitute cron, launchd, or a sleep loop as a "temporary"
  scheduler — an off-fleet timer runs outside `schedule list` and is
  invisible to every later verify step.
- F8 verify step skipped (`schedule create` run, but no `schedule
  list` check and no manual `schedule run`). Expected: the install is
  unverified — not done. An entry in the create output is not proof;
  only `schedule list` showing `tweet-watch` plus one completed
  manual run closes R9.

## Boundary values

- F9 manual verify run on a quiet watch (no new tweets, or zero HIGH
  tweets). Expected: successful run, zero `ask_human` calls, zero new
  files, exit success (R5 quiet rule). A quiet verify run still
  counts as a passing verify — the installer must not "force" a
  proposal with a fabricated tweet to make the run look active.
- F10 manual verify run with a large backlog (missed ticks, dozens of
  new tweets). Expected: the verify run emits everything since the
  last persisted id, one proposal per HIGH tweet, no batching, no
  sampling (R2/R5). The installer triages per-proposal; never trims
  state to shorten the verify.
- F11 manual verify run where the draft hits the X length limit.
  Expected: rewrite/trim before proposing, never auto-truncate
  mid-word (R5). An unpostable proposal fails the verify — fix the
  draft path, re-run once.
- F12 verify run triggered twice "to be sure" (two manual `schedule
  run` invocations back to back). Expected: the second run is quiet
  (state persisted by the first, R2 observable). If the second run
  re-proposes the same tweets, state persistence is broken — that is
  a worker bug, not a need for a third run.

## External errors

- F13 fleet scheduler daemon down or unreachable at install time
  (`schedule create` times out, connection refused). Expected: error
  naming the scheduler; retry the exact same create command later.
  Never fall back to a local cron entry "until fleet is back" — it
  becomes a second unaware ticker once the daemon returns.
- F14 `x` CLI missing or failing on the verify machine (`command not
  found`, non-zero exit on `watch check`). Expected: the manual run
  fails loud with the handle named, state untouched for the failed
  scope (M2/R2). The schedule entry itself stays installed; fix the
  CLI and re-run the manual verify once. Deleting the schedule over
  an `x` failure confuses a run-time dependency with install state.
- F15 INTERESTS.md missing or unreadable during the verify run.
  Expected: the run aborts proposals for the run (R5), tweets stay
  new via persisted state, next tick re-drives them. The installer
  must not score by gut feel to "complete the verify".
- F16 `ask_human` unreachable during the verify run (operator console
  down, tool timeout mid-batch). Expected: record the tweet as
  unproposed, continue remaining HIGH tweets, exit non-zero/log-loud
  (R5). The failure is neither a decline nor a confirmation; reply
  files are not written and the schedule entry is left in place for
  the next tick to retry.
- F17 KB parent dir missing during the verify run (`media/x/` itself
  absent). Expected: route through the R1 ensure path (`mkdir -p`
  then watchlist-ensure with the 5 seeds) and proceed. The installer
  never creates KB paths outside the documented prefixes.

## Wrong state

- F18 schedule already exists on re-install (`tweet-watch` present
  from a previous attempt; create returns "already exists" or makes a
  duplicate). Expected: never create a second entry under a variant
  name. Inspect the existing entry with `schedule list`: if cron,
  overlap, and coder match, keep it and proceed to verify; if any
  differ, delete it and recreate exactly once.
- F19 stale schedule from an older config (entry named `tweet-watch`
  but with a previous cron, missing `--overlap skip`, or an old
  coder). Expected: the documented flags win — delete the stale
  entry, recreate with the exact command, re-verify with `list` plus
  one manual run. Patching flags in place (if the CLI even allows it)
  without re-verifying leaves doubt about what actually fires.
- F20 state file corrupt during the verify run (invalid JSON, list
  instead of a handle->id map, numeric instead of string ids).
  Expected: abort-before-fetch with an error naming
  `watch_state.json` (R2/M1) — never reset to `{}`. A reset during
  verify re-emits the full history as HIGH proposals and burns the
  install's credibility. Back up, repair, validate with
  `python3 -c "import json; json.load(open(...))"`, then re-run once.
- F21 watchlist missing at verify time (fresh KB machine, no
  `watchlist.md`). Expected: the R1 ensure creates it with exactly
  the 5 seeds (`omarsar0`, `typesafeai`, `cloneisjun`,
  `goodhartproof`, `SakanaAILabs`) and proceeds. An existing
  watchlist is never overwritten to "restore" the seeds.
- F22 confirmation without a reply id during the verify run
  ("posted", no id or link in the `ask_human` answer). Expected:
  store nothing, log pending-confirmation with the source id (R6) —
  never invent an id to complete the `<date>-<id>.md` filename. The
  verify still passes for scheduling purposes; the reply file lands
  on the next confirmed answer.
- F23 source tweet deleted between fetch and proposal during verify
  (link 404s). Expected: propose once with cached text plus a
  dead-link note (R5), never silently drop the emitted tweet and
  never propose without the link.

## Concurrency

- F24 manual verify run colliding with the 30-minute tick (operator
  runs `schedule run` seconds before the cron fires). Expected: the
  installed `--overlap skip` sheds one of them; the other performs
  exactly one R1-R6 pass. Both runs may still call `ask_human`
  independently if the skip boundary was missed (manual-only
  overlap); double confirmation converges via idempotent same-path
  R6 writes. Never add lockfiles or merge state copies to "fix" this
  — last-writer-wins on forward-moving ids self-heals next tick, and
  the operator seeing a duplicate proposal is the accepted backstop.
- F25 two installers creating the schedule at once (both run `schedule
  create` in parallel; one wins, one gets "already exists", or two
  entries appear). Expected: the loser stops — re-read `schedule
  list`, and if exactly one correct `tweet-watch` entry exists,
  proceed to a single shared verify run. Never "verify twice, once
  each" — F12 already covers why the second run must be quiet.
- F26 watchlist edited during the verify run (operator adds/removes a
  handle between R1 and R5). Expected: the run works its R1 snapshot;
  the next tick picks up the edited list. Re-reading mid-run causes
  half-processed handles and skipped persistence.
- F27 state read-modify-write racing the tick during verify (manual
  run and cron tick read the same state, both persist newest ids).
  Expected: last-writer-wins is acceptable — ids move forward only,
  the newer write dominates, the next tick heals any missed key.
  Hand-merging two state copies risks reintroducing stale ids and
  re-emitting tweets as new.
