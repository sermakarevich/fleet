# tweet_watch M3 (reply-files) — failure modes

Scope: read files in `/Users/sergii/.ai/knowledge/media/x/replies/`
(`<date>-<id>.md`, existing per-tweet format: header, `> source:`,
`> reply to:`, quoted body, stats line) and write new ones in the same
format. Listing for R4 selects files from the last 3 days by filename
date prefix (`YYYY-MM-DD`), not by mtime.

## Bad or missing input (replies dir / file content)

- F1 replies dir missing (`media/x/replies/` does not exist). Expected:
  reads return `[]` (dedupe passes everything, persistence creates the
  dir with `mkdir -p` on first confirmed write). Not an error.
- F2 non-`.md` files in the dir (`.DS_Store`, `*.tmp` leftovers).
  Expected: ignored by the listing; only `*.md` is read.
- F3 filename not matching `<date>-<id>.md` (`notes.md`, `draft.txt`,
  `2026-9-5-123.md` with non-padded date). Expected: excluded from the
  last-3-days listing (no parseable date prefix); never aborts the run.
- F4 reply file with unparseable date prefix (`9999-99-99-123.md`,
  `abcd-123.md`). Expected: same as F3 — excluded from the recency
  window, run continues. A file that cannot be dated cannot prove
  recency, so it must not block, and it must not silently count either.
- F5 empty reply file (`<date>-<id>.md` is 0 bytes, e.g. truncated by an
  editor). Expected: read yields empty text; contributes nothing to the
  near-identical comparison in R4 but does not abort the run.
- F6 reply file missing the `> reply to:` line or the stats line
  (hand-edited, older variant). Expected: still read; comparison uses
  whatever body text is present. M3 never rejects a file for format
  drift — format compliance is enforced on write, not on read.
- F7 reply body with emoji, CJK text, or multi-line quotes. Expected:
  read/written verbatim as UTF-8; comparison in R4 is over the decoded
  text, never over raw bytes, so encoding never causes a false
  non-match.

## Boundary values

- F8 filename date exactly 3 days old vs 4 days old (run date
  `2026-09-26`: `2026-09-23-*.md` counts, `2026-09-22-*.md` does not).
  Expected: window is inclusive of the 3rd day (`run_date - 3 <= file_date
  <= run_date` by calendar date); off-by-one either way is a bug.
- F9 future-dated filename (`2026-09-27-*.md` while today is `2026-09-26`,
  clock skew or manual copy). Expected: excluded from the window (not
  `<= run_date`); a future file must not block drafts.
- F10 filename date vs mtime mismatch (file renamed, or copied from
  backup so mtime is today but prefix is 2 months old). Expected:
  filename prefix wins; mtime is never consulted.
- F11 empty last-3-days window (no `*.md` with a prefix in range, e.g.
  after a quiet stretch). Expected: return `[]`; all drafts pass R4.
  Not an error.
- F12 large backlog (~500 reply files in the dir). Expected: directory
  scan filters by filename prefix before reading bodies; only in-window
  files are opened. Slowness is linear in in-window files, not total.

## External errors

- F13 replies dir unreadable (permissions, e.g. `chmod 000`).
  Expected: abort the run with an error naming the dir path; do NOT fall
  back to `[]` (that would disable the R4 dedupe and risk proposing a
  near-duplicate). Same rule as M1-F10: fail closed, not open.
- F14 single in-window file unreadable (one file `chmod 000`, rest fine).
  Expected: abort with an error naming the file; same fail-closed reason
  as F13 — silently skipping one file could re-propose its wording.
- F15 write fails (disk full, read-only file at the target path).
  Expected: error naming the target path `<date>-<id>.md`; the reply is
  reported as unpersisted so the operator knows to retry, never silently
  dropped.
- F16 target file already exists (`<date>-<id>.md` from a retried run
  after a crash between write and state update). Expected: overwrite
  idempotently (same id means same posted reply); exactly one file at
  the path, no `-2` suffixed duplicates.
- F17 write with wrong `date` or `id` (caller passes posting date in a
  non-`YYYY-MM-DD` shape, or an empty id). Expected: error naming the
  bad value; no file written. M3 validates `<date>-<id>.md` shape before
  touching the filesystem.

## Wrong state (stale / corrupt content)

- F18 in-window file with corrupt body (binary garbage, truncated mid-line
  from a killed editor). Expected: read as best-effort text
  (`errors="replace"`); the file still counts as present in the window so
  a draft cannot slip past on a decoding technicality. Never delete or
  "repair" it automatically.
- F19 reply file present but its quoted body was hand-edited after posting
  (differs from what actually went to X). Expected: M3 reports file
  content as-is; it has no ground truth to detect the drift. Dedupe
  compares against the files, documented limitation.

## Concurrency

- F20 two runs write the same `<date>-<id>.md` (manual `schedule run`
  overlapping the scheduled run; installed schedule uses
  `--overlap skip` so this is manual-only). Expected: atomic write (temp
  file + rename, so readers never see a half-written file); last writer
  wins with identical content (F16 idempotence), so no corruption and no
  duplicates.
- F21 read-while-write (R4 listing runs while another process writes a new
  reply file). Expected: the listing either sees the complete new file or
  misses it (rename atomicity); it never sees a half-written body, so a
  draft is at worst proposed once more, never corrupted.
