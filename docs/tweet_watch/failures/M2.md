# tweet_watch M2 (x-fetch) — failure modes

Scope: for each handle run `x watch add user:<handle>` once (idempotent),
then `x watch check --format json`, and parse stdout JSON into a list of
`{id, handle, text, url, created_at}` records. Non-zero exit or unparseable
stdout surfaces as an error naming the handle; M2 never fabricates tweets.
Per-handle failures never poison other handles; a failed handle yields no
records and its state entry is not advanced.

## Bad or missing input (handles / CLI)

- F1 empty handle list. Expected: neither `x` command is invoked; return
  `[]`. Not an error.
- F2 handle with characters illegal in an X handle (inner spaces,
  `user!x`, `a/b`, empty string after M1 stripping). Expected: `x watch
  add user:<handle>` rejects it; surface the CLI's error naming the
  handle, yield no records for that handle, continue with the rest.
- F3 handle casing (`SakanaAILabs` vs `sakanaailabs`). Expected: passed
  through verbatim; matching of returned records to handles is
  case-insensitive, so records still attribute to the watchlist entry.
- F4 `x` CLI not installed / not on PATH. Expected: abort the run with an
  error naming the missing `x` command; return no records at all rather
  than partial results that would advance state unevenly.
- F5 record in `check` output missing `id` (null/absent). Expected: skip
  that record and report an error naming the handle; never synthesize an
  id (a fake id would corrupt R2 dedupe). Records missing only optional
  fields (`url`, `created_at`, `text`) are kept with `""` defaults.

## Boundary values

- F6 watched user has no tweets since last run. Expected: empty record
  list for that handle; its state entry is left unchanged.
- F7 high-volume account returns a large `check` payload (hundreds of
  records, multi-MB stdout). Expected: all records parsed, no truncation
  or sampling; backpressure stays in R2/R3 scoring, not in M2.
- F8 tweet text with emoji, CJK, newlines, quotes, `>`, `#`. Expected:
  preserved verbatim from the JSON parse; no re-escaping, no line
  splitting (one record stays one record).
- F9 `created_at` values out of chronological order or with mixed offsets.
  Expected: ignored for ordering/dedupe, which uses tweet `id` only;
  passed through as-is for display.
- F10 duplicate tweet id appearing under two handles (e.g. the same tweet
  surfaced for both author and retweeter). Expected: kept as two separate
  records keyed by `(handle, id)`; per-handle state (R2) dedupes each
  side independently.

## External errors

- F11 `x watch add` exits non-zero (suspended/deleted/protected account,
  auth expired, rate limit). Expected: error naming the handle plus the
  CLI's stderr tail; that handle yields no records this run, siblings
  continue, failed handle's state is not advanced.
- F12 `x watch check` exits non-zero (network down, API 429/5xx, expired
  token). Expected: error naming the `check` stage; return no records
  from that invocation (never partial stdout), leave all state entries
  untouched so the next run retries everything.
- F13 `check` exits 0 but stdout is not JSON (empty string, HTML error
  page, log line prefix). Expected: JSON parse error naming the stage;
  no records returned, state untouched, never fall back to regex
  scraping of the garbage.
- F14 `check` stdout is valid JSON but wrong shape (object instead of
  list, list items that are strings/numbers). Expected: shape error
  naming the stage; no records returned, state untouched.
- F15 `x` hangs (wedged daemon, no output). Expected: killed after the
  run's timeout; treated exactly like F12 (error naming the stage, no
  records, no state write).
- F16 warnings on stderr with valid JSON on stdout. Expected: success;
  only stdout is parsed, stderr is attached to the run log, never mixed
  into the parse.

## Wrong state (x-side watch store)

- F17 handle never added before (first run / fresh machine). Expected:
  `watch add` registers it, `check` returns its candidates, and (with no
  prior state entry) R2 treats all of them as new.
- F18 x-side watch cursor lost or reset (daemon data dir wiped, so
  `check` returns full history). Expected: M2 still returns everything
  it saw; R2's `watch_state.json` comparison bounds the blast radius to
  ids newer than stored state. M2 never second-guesses the daemon by
  dropping records itself.
- F19 x-side cursor stale (daemon returns nothing despite new tweets
  existing). Expected: empty result this run, state not advanced, so the
  tweets surface on a later run once the cursor catches up (re-emit over
  skip, same tradeoff as M1 F13).
- F20 `check` returns records for a handle not in this run's watchlist
  (stale daemon-side subscription after operator removed the handle).
  Expected: records for unrequested handles are dropped (and logged);
  only requested handles are returned.

## Concurrency

- F21 two runs overlap (manual `schedule run` during the scheduled run;
  the installed schedule uses `--overlap skip` so this is manual-only).
  Expected: no locking inside M2; concurrent `watch add` is idempotent
  by contract and concurrent `check` calls each parse their own stdout.
  Interleaved state saves follow M1 F18 (atomic temp-file + rename,
  last writer wins, duplicates preferred over silent skips).
