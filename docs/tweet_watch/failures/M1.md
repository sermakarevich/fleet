# tweet_watch M1 (kb-files) — failure modes

Scope: read/parse `/Users/sergii/.ai/knowledge/media/x/watchlist.md`
(one handle per line; ignore blank lines and `#` comments; strip leading
`@`) and load/save `/Users/sergii/.ai/knowledge/media/x/watch_state.json`
(map handle -> newest seen tweet id, string; missing file reads as `{}`).

## Bad or missing input (watchlist)

- F1 missing watchlist file: `watchlist.md` does not exist. Expected: R1
  creates it with exactly the 5 seed handles (`omarsar0`, `typesafeai`,
  `cloneisjun`, `goodhartproof`, `SakanaAILabs`, one per line), then M1
  returns them in that order. Not an error.
- F2 empty or comment-only watchlist (only blank lines / `#` lines).
  Expected: return `[]`; the run fetches nothing, proposes nothing, and
  leaves `watch_state.json` untouched. Not an error.
- F3 lines with leading `@` or surrounding whitespace (`"  @omarsar0 "`,
  `"\ttypesafeai\t"`). Expected: strip whitespace, strip one leading
  `@`, return `omarsar0`, `typesafeai`.
- F4 full-line `#` comment with leading whitespace (`"   # paused"`).
  Expected: ignored, same as a blank line.
- F5 duplicate handles (`omarsar0` twice, or `@omarsar0` + `omarsar0` after
  stripping). Expected: dedupe, first occurrence order kept; each handle
  fetched once per run.
- F6 line with characters illegal in an X handle (spaces inside the line,
  `user!x`, `a/b`). Expected: M1 does not validate beyond strip-and-`@`;
  the line is passed through and the failure surfaces at M2 as an error
  naming the handle (`x watch add` rejects it). M1 never silently drops a
  non-blank, non-comment line.
- F7 CRLF line endings or UTF-8 BOM at file start. Expected: handled by
  universal-newline/BOM-aware read; no `\r` or `\ufeff` in handles.

## Boundary values

- F8 watchlist with ~500 handles. Expected: all processed in file order,
  no truncation or sampling; slowness surfaces in fetch (M2), not in M1.
- F9 tweet ids stored as strings of differing length (snowflake growth
  over years). Expected: M1 stores and round-trips ids verbatim as
  strings, never coerces to int (no precision loss, no `1e+18` float
  formatting); newness comparison is the caller's (R2) concern.

## External errors

- F10 watchlist unreadable (permissions, e.g. `chmod 000`). Expected:
  abort the run with an error naming the watchlist path; do not fall back
  to seeds (that would mask the operator's list) and do not touch state.
- F11 watchlist path is a directory. Expected: error naming the path;
  same no-fallback, no-state-write behaviour as F10.
- F12 state file parent dir missing (`media/x/` gone). Expected: reads
  still return `{}`; on save, create parent dirs (`mkdir -p`) then write.
- F13 state save fails (disk full, read-only file). Expected: error naming
  the state path; the run's already-computed results are still returned,
  but state is not advanced, so the next run may re-emit the same tweets
  (documented duplicate-over-loss tradeoff).

## Wrong state (state file content)

- F14 corrupt state file (invalid JSON, truncated write from a killed
  prior run). Expected: abort with an error naming the state path and the
  JSON error; do NOT silently reset to `{}` (that would re-propose every
  tweet ever seen). Recovery: operator deletes or restores the file per
  RUNBOOK, then re-runs.
- F15 valid JSON but wrong top-level shape (a list, a string, `null`).
  Expected: error naming the state path and the expected shape
  (`{handle: id-string}`); no overwrite, same recovery as F14.
- F16 per-handle value of wrong type. Expected: JSON numbers are coerced
  via `str()` (lossless for snowflakes); `null`, booleans, lists, or dicts
  abort with an error naming the handle key; valid sibling entries are not
  partially saved.
- F17 state contains handles no longer in the watchlist. Expected: entries
  are preserved untouched on save (so re-adding a handle does not re-emit
  old tweets); they are simply not consulted during the run.

## Concurrency

- F18 two runs overlap (manual `schedule run` while the scheduled run is
  active; the installed schedule uses `--overlap skip` so this only happens
  manually). Expected: no file locking; writes are atomic (temp file +
  rename, so readers never see a half-written F14); last writer wins, which
  may re-emit (never silently skip) a tweet on the following run.
