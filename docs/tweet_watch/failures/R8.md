# tweet_watch R8 (runbook) — failure modes

Scope: repo file `docs/tweet_watch/RUNBOOK.md` documenting schedule
name/cadence, KB paths owned by the worker, the `x` CLI commands, how
to add/remove a watched handle, how to verify a run, and how to
recover from a missed run or corrupt state file. Observable: the file
exists and each listed procedure works as written.

Step-level edge cases (fetch/parse, scoring, dedupe, gating,
persistence, formats) live in M1/M2/M3 and R1-R6; this file covers the
runbook only: missing/wrong/stale procedures, an operator following
the runbook verbatim into a bad state, and what the runbook must say
instead (exact commands, exact paths, never destructive shortcuts).

The runbook names these exact facts — any deviation is a runbook bug:
schedule `tweet-watch`, cron `*/30 * * * *`, `--overlap skip`, coder
`opencode`; KB paths `/Users/sergii/.ai/knowledge/media/x/watchlist.md`,
`/Users/sergii/.ai/knowledge/media/x/watch_state.json`,
`/Users/sergii/.ai/knowledge/media/INTERESTS.md`,
`/Users/sergii/.ai/knowledge/media/x/replies/`; `x watch add
user:<handle>` then `x watch check --format json`; KB files never
committed to the repo.

## Bad or missing input

- F1 runbook file missing from the repo or at an undocumented path
  (operator opens `docs/tweet_watch/RUNBOOK.md` and it is not there).
  Expected: error naming the expected path; the operator does not
  reconstruct the procedure from REQUIREMENTS.md or memory. A missing
  runbook is a doc bug, never "figure it out from the bead".
- F2 runbook documents the wrong schedule identity (name other than
  `tweet-watch`, cron other than `*/30 * * * *`, missing
  `--overlap skip`, coder other than `opencode`). Expected: runbook
  bug — fix the doc. An operator following a wrong cron installs a
  duplicate or differently-cadenced schedule; `fleet schedule list`
  showing two `tweet-watch`-like entries is the signal to delete the
  wrong one and reinstall exactly as documented.
- F3 runbook lists a wrong KB path (typo in `watch_state.json`,
  `replies/` vs `reply/`, `~/.ai` vs the absolute
  `/Users/sergii/.ai/knowledge/media/x/` prefix). Expected: error
  naming the path as written; the operator never falls back to a
  "likely" path. Editing or deleting a file at a guessed path risks
  destroying the real watchlist or state.
- F4 runbook documents wrong `x` CLI invocations (`x watch check`
  without `--format json`, `x watch add <handle>` without the
  `user:` prefix, invented flags). Expected: runbook bug — the exact
  invocations are `x watch add user:<handle>` once per handle, then
  `x watch check --format json`. Output piped through ad-hoc
  text-munging instead of JSON parsing is not an acceptable
  substitute.
- F5 add-handle procedure omits the file format rules (one handle per
  line, `#` comments and blank lines ignored, leading `@` stripped).
  Expected: the runbook must state all three rules with an example
  (`cloneisjun`, not `@cloneisjun`, not a comma-separated list). An
  operator adding `@cloneisjun, goodhartproof` on one line gets one
  garbage handle, not two — M1 parses lines, not commas.
- F6 add-handle procedure tells the operator to also edit
  `watch_state.json` for the new handle. Expected: refused — a
  missing state entry means "all candidates are new" (R2), which is
  the correct first-run behavior for a new handle. Hand-inserting a
  guessed newest-id silently skips real tweets.
- F7 remove-handle procedure tells the operator to delete the
  handle's key from `watch_state.json`. Expected: unnecessary and
  forbidden — stale state keys are harmless (R2 ignores handles not
  in the watchlist) and hand-editing state risks corrupting the JSON.
  The runbook must say: delete the line from `watchlist.md`, leave
  state alone.
- F8 runbook instructs committing KB files to the repo (`git add`
  on watchlist, state, or replies). Expected: refused — KB files live
  under `/Users/sergii/.ai/knowledge/...` and are never committed
  (spec deliverables rule). The runbook must say "written directly,
  never committed".
- F9 verify-a-run procedure has no concrete expected output (says
  "check it worked" without `fleet schedule list` showing
  `tweet-watch` and what a quiet vs. proposing run looks like).
  Expected: runbook bug — the procedure must name the commands and
  the success signals (entry present in `schedule list`; quiet run =
  zero proposals, zero new files; HIGH run = one `ask_human` call per
  HIGH tweet with link + draft). Without them the operator cannot
  tell success from silent failure.
- F10 recovery procedure for a corrupt state file says to delete it
  (`rm watch_state.json`) so "it will be recreated". Expected:
  refused — deleting state re-emits every tweet ever seen as new
  (R2 observable: missing entry -> all candidates new) and spams the
  operator with duplicate proposals. The runbook must say: abort runs,
  back up the corrupt file (`cp watch_state.json
  watch_state.json.bak-<date>`), hand-repair or restore from backup,
  validate with `python3 -c "import json; json.load(open(...))"`,
  then resume.
- F11 recovery procedure for a missed run says to "replay" missed
  ticks or to run the worker N times to catch up. Expected: refused
  — the next tick self-heals (state persists newest seen ids, so one
  `fleet schedule run` picks up everything since the last success).
  The runbook must say: trigger exactly one manual
  `fleet schedule run`, never one per missed tick.

## Boundary values

- F12 watchlist reduced to zero handles (all lines deleted or
  commented out). Expected: the runbook must state this is a valid
  quiet configuration — the run fetches nothing, proposes nothing,
  exits success, leaves state unchanged. It must forbid "fixing" this
  by re-seeding the 5 seed handles (R1: existing file is never
  overwritten).
- F13 watchlist containing only blanks and `#` comments. Expected:
  same as F12 — parses to an empty handle list, successful quiet run.
  The runbook must not tell the operator this is corruption; it is
  the documented effect of M1's ignore rules.
- F14 backlog after missed runs (dozens of new tweets across handles
  on the next tick). Expected: the runbook must state the bounded
  behavior — all new tweets are emitted once, each HIGH tweet gets
  its own proposal, no batching, no sampling to "keep it short". An
  operator overwhelmed by N proposals triages per-proposal (confirm /
  decline each), never edits state to skip the backlog.
- F15 draft at or over the X length limit during a verified manual
  run. Expected: the runbook must point at the R5 rule — rewrite/trim
  before proposing, never auto-truncate mid-word. A runbook silent on
  length yields unpostable proposals the verify step cannot confirm.
- F16 runbook drift after an R1-R6 change (INTERESTS.md gains a core
  topic, reply format gains a field, `x` CLI changes output shape,
  schedule flags change, but the runbook still documents the old
  shape). Expected: the numbered requirements (R1-R6 text) win over
  the runbook copy. The operator reports the mismatch naming both
  sources instead of following the stale copy into a wrong write.

## External errors

- F17 `x` CLI missing or failing on the run machine (`command not
  found`, non-zero exit, unparseable stdout). Expected: the runbook
  troubleshooting section must name this first — fail loud with the
  handle named, state untouched for the failed scope (R2/M2), next
  run retries. "Continue with cached tweets" or hand-invented
  candidates violate M2's never-fabricates-tweets rule.
- F18 INTERESTS.md missing or unreadable at run time. Expected: the
  runbook must instruct aborting proposals for the run (R5), not
  scoring by gut feel. Tweets stay new via persisted state and are
  re-driven next run.
- F19 `fleet schedule list` not showing `tweet-watch` (entry deleted,
  scheduler down, wrong fleet context). Expected: the runbook must
  give the exact reinstall command (`fleet schedule create --name
  tweet-watch --cron '*/30 * * * *' --overlap skip`, coder
  `opencode`) and the re-verify (`schedule list` + one manual
  `schedule run`). It must forbid creating a second entry under a
  variant name as a "backup".
- F20 KB parent dir missing (`media/x/` itself absent, not just the
  files). Expected: the runbook must route through the R1 ensure path
  (`mkdir -p` then the watchlist-ensure), then proceed. The operator
  never creates directories under unlisted paths.
- F21 KB files unreadable due to permissions (`permission denied` on
  watchlist, state, or `replies/`). Expected: the runbook must say
  fix ownership/permissions (`ls -l`, `chmod`/`chown` as appropriate)
  and re-run — never `sudo`-run the worker, never move the KB files
  to a writable path. Running as another user splits state across
  homes and forks the newest-id tracking.

## Wrong state

- F22 state file corrupt when the runbook recovery section is reached
  (invalid JSON, valid JSON with wrong shape such as a list instead
  of a handle->id map, numeric instead of string ids). Expected: the
  runbook must instruct abort-before-fetch with an error naming the
  state path (R2/M1), back up first (F10), then repair — never reset
  to `{}`. A silent reset re-emits the full history.
- F23 clock skew or a long scheduler outage (no runs for days; reply
  files older than 3 days). Expected: the runbook must state both
  consequences — the next run still emits everything since the last
  persisted id (no tweets lost), but R4's 3-day window no longer
  blocks repeats of recently-proposed angles whose files aged out.
  The operator triages proposals with extra care after an outage
  instead of assuming dedupe still covers the gap.
- F24 source tweet deleted between fetch and proposal (link 404s
  during verification). Expected: the runbook must document the
  behavior — propose once with cached text plus a dead-link note
  (R5), never silently drop an emitted tweet and never propose
  without the link.
- F25 confirmation recorded without a reply id ("posted", no id or
  link in the `ask_human` answer). Expected: the runbook must say
  store nothing and log pending-confirmation with the source id
  (R5/R6), never invent an id to complete the
  `<date>-<id>.md` filename. The reply file is written on the next
  confirmed answer carrying the id.
- F26 operator already replied from outside the worker (manual reply
  on X, no file in `replies/`). Expected: the runbook must state the
  documented behavior — the worker still proposes (R5); the linked
  thread is the backstop. The runbook must not invent an "X liveness
  check" step that sends the operator beyond the documented tools.

## Concurrency

- F27 two runs overlap (manual `schedule run` colliding with the
  30-minute tick; the installed schedule uses `--overlap skip` so
  this is manual-only). Expected: the runbook must state no-locking
  semantics — both runs may propose independently (R5); double
  confirmation converges via idempotent same-path R6 writes. The
  runbook must not instruct lockfiles, state-file merges, or
  de-duplicating the other run's proposals — the operator seeing a
  duplicate proposal is the accepted backstop, and R4 blocks repeats
  once one is persisted.
- F28 two operators edit `watchlist.md` at the same time (one adds a
  handle, one removes another; last-writer-wins clobbers an edit).
  Expected: the runbook must instruct serial edits — re-read the file
  before editing, make the single-line change, save once. There is no
  merge step; concurrent multi-line rewrites lose handles.
- F29 state read-modify-write racing a concurrent run (both runs read
  the same state, both persist newest ids). Expected: last-writer-wins
  on the JSON map is acceptable — ids only move forward per handle,
  so the newer write dominates and the next tick heals any missed
  key. The runbook must forbid hand-merging two state copies, which
  risks reintroducing stale ids and re-emitting tweets.
