# tweet_watch R2 (new-tweet detection and state update) — failure modes

Scope: for each handle from R1, fetch candidate tweets via M2 and emit
only those with ids newer than the handle's entry in
`/Users/sergii/.ai/knowledge/media/x/watch_state.json` (missing entry ->
all candidates are new). After the check, persist the newest seen id per
handle back to `watch_state.json` via M1. Comparison uses the tweet `id`
only, never `created_at` or text. Fetch/parse edge cases live in M2,
file-format edge cases in M1; this file covers the compare/emit/save
contract only.

## Bad or missing input

- F1 empty handle list. Expected: no `x` invocation, emit `[]`, leave the
  state file byte-identical (no rewrite). Not an error.
- F2 handle with no state entry (first run, newly added handle, entry
  preserved per M1 F17 but never seen). Expected: every candidate for
  that handle is new; after the run its entry is set to the max
  candidate id.
- F3 M2 per-handle failure (non-zero exit or unparseable stdout naming
  the handle, illegal handle rejected by `watch add`). Expected: that
  handle emits nothing and its state entry is not advanced; sibling
  handles continue normally; the run reports the per-handle error.
- F4 corrupt state file (invalid JSON, wrong top-level shape, `null` /
  bool / list / dict value for a handle in this run). Expected: abort
  before any fetch per M1 F14-F16 with an error naming the state path
  (and handle key where applicable); emit nothing, write nothing. Never
  reset to `{}` — that would re-emit every tweet ever seen.
- F5 candidate record missing `id` (M2 F5). Expected: the record is
  skipped and never becomes the persisted newest id, even if it is the
  sole candidate (state entry left unchanged); valid siblings still emit
  and the entry advances to the max valid id.

## Boundary values

- F6 no new tweets (all candidate ids `<=` stored entry, or no
  candidates). Expected: emit nothing and leave the state file
  byte-identical — no rewrite, no timestamp touch. This is the
  second-run-no-change observable.
- F7 first run for a handle (F2) with a large backlog (hundreds of
  candidates after an x-side cursor reset). Expected: all candidates
  emit once, state jumps to the max id. No truncation or sampling to
  "catch up gradually".
- F8 id comparison across lengths (snowflake growth: stored `"999..."`.
  vs candidate `"1000..."` with more digits). Expected: numeric
  comparison on all-digit ids, not lexicographic string comparison
  (lexicographic would call `"9..."` newer than `"10..."` and
  permanently skip tweets). Non-numeric ids fall back to string
  comparison and are logged.
- F9 duplicate tweet id inside one `check` payload (same `(handle, id)`
  twice). Expected: emitted once; state advances to that id once.
- F10 single new tweet. Expected: emitted exactly once; state advances
  to exactly that id. Across two consecutive runs the tweet never
  appears twice.

## External errors

- F11 `x watch check` fails run-wide (non-zero exit, unparseable stdout,
  hang killed by timeout — M2 F12/F13/F15). Expected: emit nothing at
  all and leave every state entry untouched, so the next run retries
  everything. Never persist partial results from a failed invocation.
- F12 state save fails (disk full, read-only file — M1 F13). Expected:
  abort with an error naming the state path; the run's computed new
  tweets are still returned, but state is not advanced, so the next run
  re-emits them (documented duplicate-over-loss tradeoff).
- F13 state file disappears mid-run (operator deletes it between load
  and save). Expected: the save recreates it via `mkdir -p` + atomic
  write containing the in-memory baseline plus this run's advances;
  entries for handles not in this run's watchlist and not in memory are
  lost with the deleted file — accepted and logged, recovery per
  RUNBOOK (no silent merge with a file that no longer exists).

## Wrong state

- F14 stored id newer than everything returned (tweets deleted,
  account purged, x-side cursor moved past state). Expected: emit
  nothing and do NOT regress the stored entry backwards to the older
  candidates. State only ever moves forward or stays put.
- F15 stored id with a gap (ids 100 and 103 stored/returned, 101-102
  deleted or never surfaced). Expected: no gap-filling and no waiting;
  anything numerically greater than stored is new, state advances to
  the max returned.
- F16 state holds handles no longer in the watchlist. Expected: those
  entries are preserved untouched on save per M1 F17; they are not
  consulted, and re-adding the handle later does not re-emit old
  tweets.
- F17 x-side watch cursor reset (daemon returns full history — M2 F18).
  Expected: M2 returns everything, R2's state comparison bounds the
  blast radius to ids newer than stored; R2 never drops records itself
  to "correct" the daemon beyond the id comparison.
- F18 crash or kill between emit (proposals sent) and state save.
  Expected: on restart the same tweets re-emit (duplicate-over-loss);
  downstream R4/R5 tolerate the re-proposal and the operator sees the
  same link+draft again rather than a tweet silently skipped forever.

## Concurrency

- F19 two runs overlap (manual `schedule run` racing the scheduled run;
  the installed schedule uses `--overlap skip` so this is manual-only).
  Expected: no locking in R2; each run loads state once at start and
  saves atomically (temp file + rename per M1 F18) at end; last writer
  wins, which may re-emit (never silently skip) a tweet on the
  following run.
- F20 watchlist edited between two overlapping runs (handle added in
  run A but not run B). Expected: each run's emit/save covers only its
  own handle list; the added handle's entry appears after run A saves,
  and run B's save must merge onto run A's file rather than clobber it
  — in practice serialized by the atomic-write + reload-before-save:
  re-read the file just before saving and merge per-handle maxima, so
  the slower run never rolls back the faster run's advance.
