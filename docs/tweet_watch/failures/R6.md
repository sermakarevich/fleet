# tweet_watch R6 (reply persistence) — failure modes

Scope: when the operator confirms a reply was posted (via the
`ask_human` answer), store it as
`/Users/sergii/.ai/knowledge/media/x/replies/<date>-<id>.md`
(`date` = posting date `YYYY-MM-DD`, `id` = posted reply tweet id)
in the existing per-tweet format via M3 (header, `> source:`,
`> reply to:`, quoted body, stats line). Unconfirmed drafts store
nothing. File read/write mechanics (listing window, atomic rename,
permission errors) live in M3; this file covers the confirm-to-file
gate only: given (draft, ask_human answer), write exactly one file,
write nothing, or report the reply as unpersisted.

A confirmation is an `ask_human` answer that states the reply was
posted AND supplies the posted reply id (bare numeric id or an
x.com URL containing it). Anything less is not a confirmation —
it is unconfirmed, and the tweet is skipped, never retried as-is.

## Bad or missing input

- F1 operator declines, skips, or answers without posting ("skip",
  "not this one", rewrites it themselves elsewhere). Expected: store
  nothing (R6 observable: unconfirmed -> no new file). Not an error;
  the run succeeds.
- F2 ambiguous answer (empty answer and empty note, or text that
  neither confirms posting with a reply id nor declines). Expected:
  treated as unconfirmed — store nothing. Ambiguity is never
  interpreted as confirmation; the reply file requires a posted id.
- F3 confirmation with no reply id ("posted" with no id or link).
  Expected: store nothing yet. Logged as pending-confirmation with
  the source tweet id so the operator can supply the id; never
  invent an id.
- F4 confirmation with a malformed reply id (non-numeric string,
  truncated paste, "id: abc"). Expected: store nothing; error naming
  the bad value. If the answer contains an x.com URL, the worker
  extracts the trailing numeric id from the URL; otherwise the value
  must be all digits.
- F5 confirmation with an explicit posting date in a non-`YYYY-MM-DD`
  shape ("26/09/2026", "yesterday"). Expected: error naming the bad
  value; no file written (M3 validates `<date>-<id>.md` shape before
  touching the filesystem). A confirmation with no date at all uses
  the confirmation-day local date — that is the common case, not an
  error.
- F6 confirmed but the draft text is empty after trimming (generator
  returned nothing yet R5 proposed it by bug). Expected: store
  nothing; logged with the source tweet id. An empty file is never
  written to `replies/`.
- F7 confirmation for a tweet that was never proposed (stale answer,
  mismatched id pasted by the operator). Expected: store nothing;
  logged naming the unmatched id. R6 only stores replies for tweets
  proposed in this run — it never creates a file from an id alone
  with no draft and no source link.

## Boundary values

- F8 zero confirmations in the run (all declined, or zero HIGH
  tweets so R5 made zero calls). Expected: zero new files and a
  successful run — silence is the correct output, not an error.
- F9 N confirmations -> exactly N files (3 confirmed replies -> 3
  `<date>-<id>.md` files, each with its own reply id). Expected:
  never merged into one file, never fanned out into 2 files for 1
  reply.
- F10 run crossing midnight (run starts 23:55, operator confirms at
  00:05 next day). Expected: `date` is the posting/confirmation day,
  not the run-start day. The filename records when the reply went
  to X, so the R4 3-day window stays aligned with reality.
- F11 retried run re-confirming an already-stored reply (crash
  between write and exit, operator confirms the same reply id
  again). Expected: idempotent overwrite of the same
  `<date>-<id>.md` path — exactly one file, no `-2` suffixed
  duplicates (M3-F16).
- F12 confirmation for a reply id whose file already exists with
  different body text (operator re-posted with edits under... in
  practice X ids are unique, so this means the id was pasted wrong
  or the draft was edited after the first store). Expected:
  overwrite with the newly confirmed text and log loudly naming the
  path — last confirmed text wins; never create a second file for
  the same id.

## External errors

- F13 `ask_human` call fails (tool error, timeout, operator console
  unreachable) before any answer arrives. Expected: treated as
  unconfirmed — store nothing — and the run exits non-zero (or logs
  loudly) so the missed confirmation is visible. A tool failure is
  never treated as a confirmation.
- F14 replies dir missing (`media/x/replies/` does not exist).
  Expected: created with `mkdir -p` on first confirmed write, then
  the write proceeds (M3-F1). Not an error.
- F15 write fails (disk full, read-only file at the target path).
  Expected: error naming the target `<date>-<id>.md` path; the reply
  is reported as unpersisted so the operator knows to retry, never
  silently dropped (M3-F15). The confirmation itself is not retried
  in-run — the operator re-supplies it next run.
- F16 unconfirmed drafts leave no trace in `replies/` (no temp
  files, no `draft-*.md`, no half-written `<date>-<id>.md`).
  Expected: the dir listing before and after an all-declined run is
  identical. Staging files would pollute the R4 3-day window.

## Wrong state

- F17 operator posts different text than the draft ("posted with
  edits: <text>", or the pasted live reply differs from the draft).
  Expected: store the operator-confirmed posted text, not the stale
  draft. The file records what is actually on X — dedupe compares
  against the files, so storing the draft wording would poison R4.
- F18 source tweet deleted on X after the reply was posted (link now
  404s). Expected: still store the file with the cached source link
  and text. The file is a record of what was posted; liveness is
  not re-validated at write time.
- F19 watchlist or `watch_state.json` changed between R5 and R6
  (handle removed, state rewritten by another process). Expected: no
  effect — R6 writes only the confirmed reply file and never touches
  the watchlist or state. Persistence is independent of tracking.
- F20 operator already has a same-day reply file for the same source
  tweet under a different reply id (replied twice, or manual reply
  from outside the worker). Expected: still store the new confirmed
  file — R6 does not dedupe on write; near-duplicate prevention is
  R4's job before proposal, not R6's after confirmation.

## Concurrency

- F21 two overlapping runs both receive confirmation for the same
  tweet and both reach R6 (manual `schedule run` colliding with the
  scheduled run; the installed schedule uses `--overlap skip` so this
  is manual-only). Expected: atomic write decides (temp file +
  rename, so readers never see a half-written file); same id means
  the same path, so the second write is idempotent, not a duplicate
  (M3-F20, R5-F25).
- F22 R4 listing runs (same or another process) while R6 writes a new
  reply file. Expected: the listing either sees the complete new file
  or misses it (rename atomicity); it never sees a half-written body
  (M3-F21). At worst a concurrent draft is proposed once more, never
  corrupted.
