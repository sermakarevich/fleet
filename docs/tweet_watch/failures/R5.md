# tweet_watch R5 (HIGH-only human proposal) — failure modes

Scope: for each HIGH tweet that passes R4, call the `ask_human` tool
once with the tweet link plus a drafted reply post. The draft adds
something new (not praise-only, not a restatement) and follows the
voice notes in INTERESTS.md (plain language, no hype words, one
concrete observation or number first, teaching tone, abbreviations
explained on first use). MEDIUM/LOW tweets never trigger a proposal.
Fetch/scoring/dedupe/persistence failures live in M2/R3/R4/R6; this
file covers the proposal gate only: given (scored tweet, draft),
propose once, propose never, or rewrite first.

A proposal is one `ask_human` call per HIGH tweet containing both the
tweet link and the draft text. A call missing either half is not a
proposal — it is a bug, and the tweet is skipped, not retried as-is.

## Bad or missing input

- F1 HIGH tweet record with empty or whitespace-only text (deleted or
  withheld tweet that still came back from `x watch check`). Expected:
  skipped, never proposed — there is nothing to add something new to.
  Logged with tweet id; rest of the batch still processed.
- F2 HIGH tweet record missing `url` or `id` (malformed M2 record that
  slipped through). Expected: skipped — a proposal without a link is
  not a proposal per the R5 observable. Logged naming the handle;
  never invent a URL.
- F3 draft is praise-only ("Great point!", "So true 👏") or a
  restatement of the original tweet with no new content. Expected: not
  proposed; flagged for rewrite or dropped. Proposing it would violate
  the adds-something-new rule on its face.
- F4 draft uses hype words banned by INTERESTS.md voice notes
  ("game-changer", "revolutionary", "insane alpha", "mind-blowing").
  Expected: rewritten before proposing, never proposed as-is. The
  voice check happens before the `ask_human` call, not after.
- F5 draft uses an abbreviation without explaining it on first use
  ("cut your FPR with a second-pass VLM" — neither FPR nor VLM
  expanded). Expected: rewritten (expand on first use per voice
  notes), never proposed as-is.
- F6 draft that buries the concrete content (three sentences of setup
  before the first observation or number). Expected: rewritten to lead
  with the concrete observation or number per the voice notes; not
  proposed in setup-first shape.
- F7 MEDIUM/LOW tweet handed to R5 by an upstream bug (wrong label,
  R3 mis-score). Expected: never proposed — the HIGH-only gate is
  re-checked here, not trusted blindly. Logged with the label so the
  scoring bug is visible.
- F8 INTERESTS.md missing or unreadable at proposal time (voice notes
  unavailable). Expected: abort proposals for the run with the error;
  do NOT propose drafts that cannot be voice-checked. Tweets stay new
  (state already persisted by R2) and are re-driven next run.
- F9 draft is empty after trimming (generator returned nothing).
  Expected: skipped, logged with tweet id; not proposed as an empty
  call.

## Boundary values

- F10 zero HIGH tweets in the run (all LOW, or no new tweets).
  Expected: zero `ask_human` calls and a successful run — silence is
  the correct output, not an error and not a "nothing to report"
  proposal.
- F11 N new HIGH tweets -> exactly N proposals, one call each (3 HIGH
  tweets -> 3 calls). Expected: never batched into a single
  multi-tweet call and never fanned out into 2 calls for 1 tweet.
  Each call carries its own link + draft.
- F12 draft at or over the X post length limit ( overlong benchmark
  paragraph, ~300+ chars). Expected: rewritten/trimmed before
  proposing — never proposed over-limit, never auto-truncated
  mid-word or mid-number by the worker. The operator sees only
  postable drafts.
- F13 duplicate tweet id appearing twice in the R2 batch (same id
  listed under two handles, e.g. a quote-tweet attributed twice).
  Expected: proposed once; the second occurrence is dropped as a
  duplicate before the `ask_human` call.
- F14 draft that is only trivially different from the source tweet
  (copies the tweet's sentence and appends "Exactly."). Expected:
  treated as a restatement (F3), not proposed.

## External errors

- F15 `ask_human` call fails (tool error, timeout, operator console
  unreachable) for one tweet mid-batch. Expected: that tweet is
  recorded as unproposed and the run continues with the remaining
  HIGH tweets; the run exits non-zero (or logs the failure loudly)
  so the missed proposal is visible. A tool failure is never treated
  as a decline and never treated as a confirmation.
- F16 `ask_human` answer is ambiguous (empty answer and empty note,
  or text that neither confirms posting with a reply id nor declines).
  Expected: treated as unconfirmed — store nothing per R6. Never
  interpret ambiguity as confirmation; the reply file requires a
  posted reply id.
- F17 operator declines the draft or replies without posting (says
  "skip", "not this one", rewrites it themselves elsewhere).
  Expected: store nothing for that tweet (R6: unconfirmed -> no new
  file). Not an error; the run succeeds.
- F18 operator confirms posting but gives no reply tweet id (says
  "posted" with no id or link). Expected: store nothing yet — the R6
  path needs `<date>-<id>.md`. Logged as pending-confirmation with
  the source tweet id so the next run/operator can supply the id;
  never invent an id.

## Wrong state

- F19 tweet deleted on X between fetch and proposal (link now 404s).
  Expected: still proposed once with the cached text and a note that
  the link may be dead — the worker does not re-validate liveness;
  the operator decides. Never silently drop it (R2 already emitted it
  as new) and never propose without the link.
- F20 R4 pass flag missing or stale (dedupe result absent for a HIGH
  tweet, e.g. R4 was skipped by a code path bug). Expected: tweet is
  NOT proposed — no dedupe verdict means no proposal. Fail closed;
  proposing without the R4 check risks the exact near-duplicate R4
  exists to stop.
- F21 operator already replied to the tweet from outside the worker
  (manual reply exists on X but no file in `replies/`, so R4 passed
  it). Expected: still proposed — R5/R4 only know persisted files,
  not X itself. Duplicate-posting risk is accepted and documented;
  the operator seeing their own prior reply in the linked thread is
  the backstop.
- F22 HIGH tweet for a handle since removed from the watchlist
  (watchlist edited mid-run between R1 and R5). Expected: still
  proposed this run — R5 works the R1 snapshot, not a re-read. Next
  run picks up the edited list.

## Concurrency

- F23 overlapping runs proposing the same HIGH tweet (manual
  `schedule run` colliding with the scheduled run; the installed
  schedule uses `--overlap skip` so this is manual-only). Expected: no
  locking — both runs call `ask_human` independently. The operator
  seeing the same link + similar draft twice is the dedupe; once one
  is confirmed and persisted via R6, the next run's R4 blocks repeats.
- F24 operator confirms tweet A while the worker is still proposing
  tweet B (confirmation lands mid-batch). Expected: no effect on B —
  proposals are independent calls; confirmations apply per-tweet via
  R6. No batch abort, no cross-tweet state.
- F25 two overlapping runs both receive confirmation for the same
  tweet and both reach R6. Expected: R6 atomic write decides (second
  write to the same `<date>-<id>.md` path is idempotent, not a
  duplicate) — R5 itself does no coordination beyond one-call-per-tweet
  per run.
